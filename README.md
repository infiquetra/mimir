# Mimir

A cross-platform EVE Online companion app that unifies character management, skill planning, market tools, and industry features into a single, modern application.

[![CI](https://github.com/infiquetra/mimir/actions/workflows/ci.yml/badge.svg)](https://github.com/infiquetra/mimir/actions/workflows/ci.yml)
[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](https://www.gnu.org/licenses/agpl-3.0)

## Overview

Mimir aims to replace the need for multiple disconnected EVE tools (EVEMon, Pyfa, jEveAssets, etc.) with a unified, cross-platform experience. Built in Rust with egui (eframe) as a single-window desktop app. The earlier Flutter implementation was retired on the `rust-rewrite` branch; see `docs/rust-rewrite-design.md` for the parity map and deferred features.

### What works today (Rust Phase 1)

- **Multi-character dashboard**: every authorized character with wallet balance, current training skill and finish countdown, queue length, and total skill points; click to switch
- **Characters**: EVE SSO sign-in (OAuth2 PKCE on localhost), character detail with resolved corporation/alliance names, logout and delete. The same view shows read-only character detail — online status, current location and ship, attributes, active implants, jump clones, and standings, all with resolved names — and the dashboard location/ship cell fills from the same data. Attributes and active implants load with the scopes first sign-in already grants; jump clones, standings, location, ship, and online state need the step-up scopes `esi-clones.read_clones.v1`, `esi-characters.read_standings.v1`, `esi-location.read_location.v1`, `esi-location.read_ship_type.v1`, and `esi-location.read_online.v1`, which first sign-in deliberately does not request. When a character lacks them, the Characters view offers "Re-authorize with EVE SSO" (the same step-up flow as Assets: approving as a different character is rejected and nothing is saved), and a missing scope degrades only its own section. This step-up path, like the Assets one below, has not been live-verified against a real EVE account yet. Access-token signatures are verified against EVE's published JWKS signing keys (issuer, audience, and expiry checked) before any token is saved at sign-in, step-up, and refresh; a token that fails verification is rejected and nothing is saved. This verification is covered by the test suite with locally generated keys but has not been live-verified against a real EVE account yet. Character portraits come from EVE's public image service (no EVE scope needed), are cached on disk in the app cache directory, and show in the character switcher list, the active-character detail, and a Dashboard portrait column; while a portrait is loading, after a fetch failure, and in demo mode, an initial-letter placeholder is shown instead — never a fabricated or stock face — and demo mode fetches no portraits at all. The live portrait fetch is covered by tests against a local mock server but has not been live-verified against the real EVE image service yet. Corporation and alliance logos come from the same public image service (also no EVE scope needed), through the same bounded cache-first pipeline, and show beside the resolved corporation and alliance names in the active-character detail; a logo is requested only for a corporation or alliance id that EVE's own data for a known character supplied, never for a typed or searched id. While a logo is loading, after a fetch failure, and in demo mode, a blank box is shown instead — never a fabricated logo and never another corporation's or alliance's logo — and demo mode fetches no logos at all. The live logo fetch is likewise covered by tests against a local mock server but has not been live-verified against the real EVE image service yet. Standings rows in the same detail show the standing entity's logo the same way: a faction standing shows that faction's logo and an NPC-corporation standing shows that corporation's logo, each requested only for an id the character's own loaded standings supplied, with the same blank box while loading, after a failure, and in demo mode; agent, alliance, and other standings stay text-only with no icon. The live standings-icon fetch is likewise covered by tests against a local mock server but has not been live-verified against the real EVE image service yet
- **Skills**: training queue with per-skill countdowns and progress, trained-skill catalogue grouped and searchable from the bundled SDE extract. Local skill plans per character with SP and training-time estimates (stored on this device; never sent to EVE). Estimates use the character's current attributes as loaded and ignore the training queue and any future attribute remap; in demo mode plans are kept in memory for the session only. The catalogue and the plan skill picker show each skill's prerequisites (name and required level, from the same bundled SDE extract), and the picker and plan detail warn when a skill's direct prerequisites are not met at the character's trained levels. Those warnings are advisory only — they never block adding an entry — and they use trained levels only: skills already in the plan or in the training queue are not counted as trained, so a correctly ordered plan can still warn until the character actually trains. Catalogue skill rows in an expanded group show each skill's type icon from EVE's public image service (no EVE scope needed) through the same bounded cache-first pipeline as portraits and logos; an icon is requested only for one of the bundled SDE extract's skill types — the one icon source that is bundled reference data rather than a character's loaded data, because the catalogue lists untrained skills that no loaded character data names — never for a typed or searched number, and only for rows actually shown: collapsed groups show and fetch nothing, at most the first 100 skill rows matching the search are shown across all groups, with a "Showing 100 of N skills." line when an expanded group is cut short by that cap, while prerequisite lines and group headings stay text-only and no raw skill number is shown. The plan skill picker shows the same type icon beside each listed skill the same way, requested only for rows actually shown under its own separate cap: at most the first 100 skills matching the picker search are shown — a row past that cap, including its level buttons, is not shown until the search is narrowed — with a "Showing 100 of N skills." line when more match, while prerequisite and warning lines stay text-only. While an icon is loading, after a fetch failure, and in demo mode, a blank box is shown instead — never a fabricated icon and never another skill's icon — and a skill the image service has no icon for keeps that blank box beside its correct name; demo mode fetches no skill icons at all. The live skill-icon fetch is covered by tests against a local mock server but has not been live-verified against the real EVE image service yet, and which of the bundled skills actually have icons there has not been probed. The training queue and the entries already in a plan stay text-only with no icons
- **Wallet**: balance, journal and transactions with resolved counterparty/item/location names, period filters, income/expense/net analytics by reference type and counterparty, loyalty points
- **Assets**: character asset list grouped by resolved location with search and custom ship names. Reading assets needs the EVE SSO scope `esi-assets.read_assets.v1`, which first sign-in deliberately does not request. The live view is reachable after an in-app step-up grant: when a character lacks the scope, the Assets view offers "Re-authorize with EVE SSO", which opens EVE SSO in your browser asking for the already-granted scopes plus this one; approving as a different character is rejected and nothing is saved. Locations inside player-built structures resolve by name once the character also grants `esi-universe.read_structures.v1` through the same step-up flow, offered from this view; until then, and for structures the character cannot dock at, those locations honestly read "Unknown Location" (resolved names are shared with Wallet, Industry, and character location once looked up). Asset rows show item type icons from EVE's public image service (no EVE scope needed) through the same bounded cache-first pipeline as portraits and logos; an icon is requested only for an item type in the active character's own loaded assets, never for a typed or searched number, and only for rows actually shown — at most the first 100 rows matching the search are shown, with a "Showing 100 of N items." line when more match, while location headings stay text-only with no icons and no raw item number is shown. While an icon is loading, after a fetch failure, and in demo mode, a blank box is shown instead — never a fabricated icon and never another item's icon — and demo mode fetches no asset type icons at all. The live asset type-icon fetch is covered by tests against a local mock server but has not been live-verified against the real EVE image service yet. This step-up path has not been live-verified against a real EVE account yet. `--demo` mode shows the full view with sample data
- **Market**: read-only market view for one item type at a time. Public regional orders and price history in five hub regions (The Forge, Domain, Sinq Laison, Metropolis, Heimatar) need no sign-in and no EVE scope. Your own open orders need the EVE SSO scope `esi-markets.read_character_orders.v1`, which first sign-in deliberately does not request; when a character lacks it, the Market view offers "Re-authorize with EVE SSO" through the same step-up flow as Assets (approving as a different character is rejected and nothing is saved), and a missing scope affects only that one section. Item name lookup needs the item's exact EVE name. The selected item's header shows its item type icon from EVE's public image service (no EVE scope needed) through the same bounded cache-first pipeline as portraits and logos; an icon is requested only for the one selected item type — a selection is made only from the name lookup's results or the quick-pick items you hold, never from a typed number — so quick-pick rows, lookup results, and order rows stay text-only with no icons, and no raw item number is shown. While the icon is loading, after a fetch failure, and in demo mode, a blank box is shown instead — never a fabricated icon and never another item's icon — and demo mode fetches no market type icon at all. The live market type-icon fetch is covered by tests against a local mock server but has not been live-verified against the real EVE image service yet. The view also carries a per-unit trade calculator: you type a buy price, a sell price, and your own broker-fee and sales-tax percents (starting values 1.0% and 2.0%, never read from your character's skills, standings, or the station or structure), and it shows total cost, net revenue, profit per unit, margin, total fees, and the break-even sell price, with the broker fee on both orders and sales tax on the sell order only; relist fees and quantity totals are not included, figures are rounded only for display, and an empty or invalid field shows guidance instead of any figure. Nothing market-related is stored and no order can be placed; the only profit figure is the calculator's per-unit estimate from values you type, and there is no valuation feature. This path has not been live-verified against a real EVE account yet. `--demo` mode shows the full view with sample data
- **Industry**: read-only industry view for the active character. Industry jobs show activity and status in words, facility names, and finish countdowns; the blueprint library is searchable (originals and copies, sorted by name) with efficiency and run information. Both sections need the EVE SSO scopes `esi-characters.read_blueprints.v1` and `esi-industry.read_character_jobs.v1`, which first sign-in deliberately does not request; when a character lacks them, the Industry view offers "Re-authorize with EVE SSO" through the same step-up flow as Assets (approving as a different character is rejected and nothing is saved), and a missing scope affects only its own section. The view also carries an invention calculator: you type a base probability as a fraction (0.30 means 30%), your encryption and two datacore skill levels, and a decryptor multiplier (starting values 0.30, each skill level 4, and 1.0, never read from a blueprint, your character's skills, a decryptor you own, or a past job), and it shows the invention chance, capped at 100%, rounded only for display; an empty or invalid field shows guidance instead of any figure. The view also carries a reaction calculator: you choose a reaction formula by name from Mimir's bundled industry data (one bundled formula has no name in the item data and cannot be chosen), type the runs and a facility material bonus percent (starting values 1 and 0.0%, never read from a structure you use, a formula or materials you own, or your character, and never checked against them), and it shows each input material and the output product by name, the bonus applied to the total input amount and rounded with a minimum of 1, outputs at the per-run amount times runs; no chosen reaction, an empty or invalid field, or a run count too large to calculate with shows guidance instead of any quantity. The view also carries a production-chain calculator: you choose an item by name from Mimir's bundled industry data (an item with no name in the item data, or made by more than one bundled blueprint, cannot be chosen), type how many you want (starting value 1, never read from a blueprint you own or your character, and never checked against them), and it shows the item's full chain by name, each makeable item expanded into the materials for the whole runs needed to make at least the quantity shown, leftovers from a part-used run not subtracted from other lines, items made by more than one blueprint and items appearing inside their own chain shown without expansion, and no blueprint material efficiency, facility bonus, or skill applied; no chosen item, an empty or invalid quantity, or a quantity too large to calculate with shows guidance instead of any quantity. There is no cost or profit calculator. Nothing industry-related is stored, and no job can be started, cancelled, or delivered. This path has not been live-verified against a real EVE account yet. `--demo` mode shows the full view with sample data
- **Planets**: read-only Planetary Industry view for the active character. The colonies list shows resolved solar-system names, the planet type in words, upgrade level, pin count, and last-update date; selecting one colony shows its summary — whether an extractor is running and, when one is, how long until the next extractor completes (an expired or expiry-less colony shows no time rather than a guess) — plus pin counts by resolved pin type, extractor products, what each factory pin is set up to make — the installed schematic's name with its per-cycle output, inputs, and cycle time from Mimir's bundled planet schematics (a schematic the bundled data does not contain is shown as such rather than guessed), and stored items aggregated from pin contents. Both sections need the EVE SSO scope `esi-planets.manage_planets.v1`, which first sign-in deliberately does not request; when a character lacks it, the Planets view offers "Re-authorize with EVE SSO" through the same step-up flow as Assets (approving as a different character is rejected and nothing is saved), and a missing scope affects only its own section. Nothing planetary is stored, no colony can be edited or created, no extractor can be restarted, and there is no production or setup calculator. This path has not been live-verified against a real EVE account yet. `--demo` mode shows the full view with sample data
- **Fittings**: saved-fittings library for the active character. Saved fittings are listed searchable by fitting name and resolved ship name; selecting one shows its items with resolved names grouped by slot section, and "Copy as EFT" copies the selected fitting to the clipboard in EFT format (items whose names have not resolved yet are skipped with a disclosed count, never shown as numbers), and "Copy as DNA" copies it as a DNA fitting link (drones, fighters, and cargo are left out with a disclosed count, because DNA links hold fitted modules only). Selecting a saved fitting also offers "Edit a copy in Mimir": one click converts that saved fitting into an editable in-memory copy shown above the saved list — described as copied from your saved fittings, never as imported or created — keeping the saved fitting's name as written, its ship, and every item whose place in the saved fitting an edited copy can hold; any item that cannot be copied (including fitted service modules, which an edited copy cannot hold, and items whose names have not loaded yet) is left out with its reason listed with the copy, never guessed into a slot or into cargo, saved slot numbers are renumbered from the first slot in each section without changing which section anything sits in, no loaded charge is assumed for any module (saved fittings carry none), and the saved fitting's notes are not carried into the copy. Editing changes only the copy in Mimir — the saved fitting in EVE stays as it is (EVE offers no way to update a saved fitting), clicking replaces the fitting already shown above without a separate confirmation and disarms any armed save, save-a-copy, or delete confirmation, and saving the copy adds a new fitting in EVE while the saved fitting it was copied from stays as it is; a fitting with no ship, or whose ship name has not loaded yet, cannot be copied and says so without disturbing the fitting already shown. A new fitting can also be started from scratch in the view: under "Start a new fitting" you search the bundled ship list by name and click a hull — only ships the bundled catalogue proves can start an empty fitting are listed (404 ships in the current bundled catalogue, shown 100 at a time with a count), and clicking one creates an empty in-memory fitting named "New (ship) Fit" for that hull, replacing any fitting already shown below without a separate confirmation and disarming any armed save confirmation so nothing replaced can be sent to EVE by mistake; a fitting started this way is described as created, never as imported, it can be edited, renamed, and copied back as header-only EFT or a hull-only DNA link exactly like an empty import, and it cannot be saved to EVE until it holds at least one item that fits an EVE fitting slot. EFT text or a DNA fitting link can also be pasted or typed into the view to see a local imported fitting — every ship and module name is resolved against a bundled catalogue, any line or DNA segment that cannot be imported is shown with its reason instead of being dropped, and the result can be copied back as EFT or as a DNA link; importing makes no network calls and needs no EVE scope. An imported fitting or a copy of a saved fitting can now be saved to EVE, and a saved fitting can be deleted from EVE, each behind an explicit in-view confirmation; items EVE cannot represent are named in that confirmation and left out, never silently, and after a save or delete the list refreshes from EVE (EVE caches the list for up to five minutes, so a change can take that long to appear). Reading fittings needs the EVE SSO scope `esi-fittings.read_fittings.v1`, which first sign-in deliberately does not request; when a character lacks it, the Fittings view offers "Re-authorize with EVE SSO" through the same step-up flow as Assets (approving as a different character is rejected and nothing is saved), and a missing scope affects only this view. Saving and deleting additionally need the separate scope `esi-fittings.write_fittings.v1`, which first sign-in also deliberately does not request and which is offered through the same step-up flow when a character lacks it; demo mode performs no writes. Nothing fitting-related is stored locally: an imported, created, or copied fitting is kept only in memory on this device until you save it to EVE, and it is gone when you switch characters or close Mimir. An imported, created, or copied fitting can be edited in the view before it is copied or saved: items can be added by their exact name in Mimir's bundled catalogue or by browsing items and clicking a row to add it (a fitted item is added only when that bundled data proves which slot it fits, and drones, fighters, and cargo are added with a quantity; an item that cannot be placed that way is refused with its reason shown, never guessed into a slot), an item row can be removed (a removed module's loaded charge goes with it), a drone, fighter, or cargo row's quantity can be set, a fitted module row's loaded charge can be set, changed, or cleared on its own item row by typing the charge's exact name in Mimir's bundled catalogue (a charge can be set only when that bundled data lists it as a kind that module can be loaded with; the charge's size is not checked, a module the bundled data lists nothing for shows no charge box unless it already carries an imported charge, which stays clearable, and charges are still left out when the fitting is copied or saved, with that count disclosed), the fitting can be renamed, and its ship can be changed under "Change ship" inside the editor by searching the same bundled ship list (404 ships, shown 100 at a time) and clicking a hull — only the ship changes: the fitting name (a created fitting still named for its old ship keeps that name until you rename it), its imported, created, or copied description, every item, and every loaded charge stay exactly as they are, items that do not fit the new ship are kept, never removed or blocked, with any over-capacity shown in the readouts below, which are worked out again for the new ship, picking the ship the fitting is already on changes nothing, and a ship change disarms any armed save confirmation so it must be re-read before anything is sent to EVE; the separate "Start a new fitting" chooser above still starts an empty fitting and replaces the one below, unchanged. The item browser appears with the imported fitting it adds to: seven section tabs (High, Med, Low, Rig, Subsystems, Drones, and Fighters) and a search by name list only items that the bundled catalogue proves can be added to that section, so clicking a listed fitted module, rig, or subsystem always adds it through the same add path and refusal wording as typing its exact name, a row shows CPU and power grid figures only when the catalogue carries them (never an item number), and a drone or fighter click uses the quantity already typed in the add row or one when that box is blank; there is no Cargo tab, because cargo has no proven set to browse (cargo is still added by typing its exact name with a quantity), and no drag and drop. Edits change only that in-memory imported fitting — saved EVE fittings are never edited (changing a draft's ship changes only that in-memory draft's ship, never a saved fitting in EVE), there is no undo, and re-importing restores the original — every readout below recomputes from the edited fitting, the edited fitting is what the copy and save buttons use, and editing disarms an armed save confirmation so it must be re-read before anything is sent to EVE. Selecting a saved fitting or importing one also shows its CPU and power grid use against the ship's output, with the amount left, from Mimir's bundled item data; when the owning character's skill data is loaded, the ship outputs include CPU Management and Power Grid Management at that character's trained levels (base values otherwise) and module needs are reduced by Weapon Upgrades, Advanced Weapon Upgrades, Energy Grid Upgrades, Electronics Upgrades, and Shield Upgrades at that character's trained levels — the base need figures are still shown beside the reduced ones, and any module whose reduction cannot be proven from the bundled item data is counted at full need with that disclosed — while implants, and bonuses and reductions from modules, rigs, subsystems, and the ship itself are still not applied, so these numbers can differ from EVE. The same saved or imported fitting details also show the ship's base shield, armor, hull, capacitor capacity, max speed, shield/capacitor recharge times, and peak shield/capacitor recharge rates from Mimir's bundled item data, with fitted modules, rigs, subsystems, skills, implants, and ship bonuses not applied, so these base values can also differ from EVE. The same details also show shield peak recharge with fitted module bonuses — the peak passive shield recharge worked out from the hull's shield hit points and shield recharge time with the fitted modules' and rigs' shield hit point and shield recharge bonuses from that bundled item data applied (shield extenders, shield rechargers, shield flux coils, shield power relays, and the like) — with every fitted module counted as active, shield boosters and other repair not included (it is the peak of passive recharge only, not a sustained or average rate), and ship bonuses, subsystems, skills, implants, and shield changes from anything outside the ship not applied; fitted modules whose hit point or shield recharge bonus that bundled data cannot describe, and fitted modules missing from it, are left out with disclosed counts per dimension, never summed and never counted as zero bonus, and where that bundled data has no complete shield hit point and shield recharge data for the ship, the readout says so instead of showing a figure. The same details also show the bare hull's base shield, armor, and hull damage resistances (EM, thermal, kinetic, and explosive) from that bundled item data, again with fitted modules, rigs, subsystems, skills, implants, and ship bonuses not applied, so those base-only resistances can also differ from EVE's fitted values. The same details also show the ship's resistances with fitted module and rig resistance bonuses from that bundled item data applied to those base values (stacking penalties where modules of the same kind pile up; every fitted module counted as active, because the fitting data does not say which modules are on; ship bonuses, subsystems, skills, and implants not applied; fitted modules whose resistance bonus that bundled data cannot describe, and fitted modules missing from it, left out with a disclosed count instead of being counted as zero bonus) — and the effective hit points below are shown both from the base values and with these resistance bonuses and fitted hit point bonuses. The same details also show base effective hit points computed from the bare hull's base hit points and resistances in that bundled item data, against omni damage — equal quarters EM, thermal, kinetic, and explosive — with fitted modules, rigs, subsystems, skills, implants, and ship bonuses not applied, and a different damage mix would give different numbers. The same details also show effective hit points with fitted module resistance and hit point bonuses computed from the hull's hit points with the fitted modules' and rigs' hit point bonuses applied (shield extenders, armor plates, and the like), divided by those bonused resistances, against the same omni damage — equal quarters EM, thermal, kinetic, and explosive — with every fitted module counted as active, ship bonuses, subsystems, skills, implants, and resistance or hit point changes from anything outside the ship not applied, fitted modules whose resistance or hit point bonus that bundled data cannot describe, and fitted modules missing from it, left out with disclosed counts (the missing-module count is the same as in the resistances readout) instead of being counted as zero bonus, and a different damage mix would give different numbers. The same details also show bay usage at base values — cargo bay volume used against the ship's base cargo capacity, drone bay volume and drone bandwidth used against the ship's base drone bay capacity and bandwidth, and fighter bay volume used where the ship has a fighter bay — as plain sums of item volumes and per-drone bandwidth from that bundled data, with capacity bonuses from skills, modules such as cargo expanders, rigs, subsystems, implants, and the ship itself not applied and specialized holds (such as ore, ammo, and fleet hangars) not counted, so these numbers can also differ from EVE; items whose volume or bandwidth is not in the bundled data are left out of those sums with a disclosed count where the ship has that bay, never counted as zero. The same details also show rig calibration used against the ship's base calibration, as plain sums of base rig calibration costs from that bundled data, with skills, implants, and bonuses from modules, rigs, subsystems, and the ship itself not applied, so these numbers can also differ from EVE; rigs whose calibration cost is not in the bundled data are left out of the sum with a disclosed count, never counted as zero. The same details also show the ship's base slot layout — fitted low, medium, high, rig, and subsystem slots against the hull's base slot counts, and turret and launcher hardpoints fitted against the hull's base hardpoints — counted from the fitted slot flags and bundled hardpoint markers, with slot and hardpoint changes granted by subsystems, skills, implants, and bonuses from modules, rigs, and the ship itself not applied, so these base numbers can also differ from EVE's fitted layout; on tech-3 hulls, whose layout comes from their fitted subsystems, only the rig and subsystem counts are shown, with a note saying why, instead of bare-hull numbers that would mislead, and high-slot modules missing from the bundled data are left out of the hardpoint counts with a disclosed count, never counted as using no hardpoint. The same details also show the bare hull's base navigation and targeting values — warp speed, align time, mass, signature radius, targeting range, scan resolution, sensor strengths (RADAR, Ladar, Magnetometric, and Gravimetric), and max locked targets — from that bundled item data, with fitted modules, rigs, subsystems, skills, implants, and ship bonuses not applied, so these base values can also differ from EVE. The same details also show base damage per second per weapon family (turret, launcher, drone, and fighter) from that bundled item data, with no combined damage-per-second total, plus — on a fitting draft with recorded charges (an imported EFT fitting, or any draft with a charge set on a module's item row) — volley (the turret and launcher damage in one firing cycle from those same recorded charges; drone and fighter damage is not in the volley) and turret optimal and falloff ranges (averages of the fitted turrets' base ranges, weighted by each turret's share of the turret volley, and each shown only when every counted turret has that range in the bundled data); turret and launcher damage counts only a loaded charge recorded with its module, listed after the module in imported EFT text or set on the module's item row in a fitting draft, counted exactly as recorded — saved fittings record no loaded charges and no charge is assumed, so those weapons are counted as unloaded instead of being given a guessed charge — while drone damage is capped by the ship's base drone bandwidth and fighter damage by its base fighter tubes, and skills, implants, bonuses from modules, rigs, subsystems, and the ship itself, tracking, missile application, reload time, and flight time are not applied (every shot is counted at full damage), so these base numbers can also differ from EVE; items whose damage data is not in the bundled data are left out with a disclosed count, never counted as zero. The same details also show a base capacitor-stability figure — whether the fitted modules whose base capacitor use is in Mimir's bundled item data, cycling continuously, settle or empty the bare hull's base capacitor — with capacitor boosters, skills, implants, and bonuses from modules, rigs, subsystems, and the ship itself not applied; modules whose base capacitor use is not in the bundled data are left out with a disclosed count, never counted as zero. The same details also show capacitor stability with fitted module bonuses — the same module capacitor use, peak recharge, and settle-or-empty verdict with the fitted modules' and rigs' capacitor capacity and recharge bonuses from that bundled item data applied to the hull's base capacitor (capacitor batteries, rechargers, and the like), cycling continuously — with every fitted module counted as active, module capacitor use still at base values (bonuses to how much capacitor a module needs or how fast it cycles are not applied), ship bonuses, subsystems, skills, implants, capacitor boosters, and capacitor changes from anything outside the ship not applied, and effects on other ships not modelled; fitted modules whose capacitor capacity or recharge bonus that bundled data cannot describe, and fitted modules missing from it, are left out with disclosed counts per dimension, never summed and never counted as zero bonus. The same details also show base active repair per hit-point layer — raw base hit points per second from the fitted shield boosters, armor repairers, and hull repairers in Mimir's bundled item data, cycling continuously — with resistances, skills, implants, bonuses from modules, rigs, subsystems, and the ship itself, loaded charges, and reload time not applied; repair modules whose base repair data is not in the bundled data are left out with a disclosed count, never counted as zero, and remote repairers are not counted. The shield peak recharge with fitted module bonuses, the resistances with fitted module bonuses, the effective hit points with fitted module resistance and hit point bonuses, and the capacitor stability with fitted module bonuses above are the four adjusted fitting readouts (the shield peak recharge bonuses only the shield hit points and shield recharge time it divides, as a passive peak with no shield booster or other repair included; the effective hit points bonuses both the hit points it starts from and the resistances it divides by; the capacitor stability bonuses only the ship's capacitor capacity and recharge, with module capacitor use still at base values); every other figure stays base-only (the damage-per-second figures above are base values per weapon family, with no combined damage-per-second total; the volley and turret-range figures above are likewise base values, shown only where a fitting draft records charges as above), and there are no other adjusted (fitted) fitting totals of any kind. The selected saved fitting's ship line and item rows show item type icons from EVE's public image service (no EVE scope needed) through the same bounded cache-first pipeline as portraits and logos; an icon is requested only for a ship or item type id in the active character's own loaded saved fittings, never for a pasted or typed id, so the fittings list and imported-fitting details stay text-only with no icons. While an icon is loading, after a fetch failure, and in demo mode, a blank box is shown instead — never a fabricated icon and never another item's icon — and demo mode fetches no type icons at all. The live type-icon fetch is covered by tests against a local mock server but has not been live-verified against the real EVE image service yet. This path, including the new save and delete writes, has not been live-verified against a real EVE account yet. `--demo` mode shows the full view with sample data
- **Exploration**: read-only offline wormhole reference (types by code with destination and mass limits, J-space and special systems, and the six system-effect families) from bundled CCP SDE data. It needs no sign-in and no EVE scope, makes no network calls, and stores nothing. Live connection feeds, a signature notebook, and route planning are not implemented
- **Settings**: startup view, keyboard shortcuts (1-9, 0, E views, Ctrl/Cmd+R refresh, `/` search, PgUp/PgDn character cycle), filterable in-app log view
- **Offline-first**: refreshes persist to local SQLite and render from cache at next launch; `--demo` mode runs the full UI on bundled sample data with no credentials or network

## Getting Started

### Prerequisites

- Rust toolchain (stable, with `rustfmt` and `clippy`)
- Linux GUI build libraries for egui (xcb/wayland/xkbcommon development packages)

### Development Setup

```bash
# Clone the repository
git clone https://github.com/infiquetra/mimir.git
cd mimir

# Run with bundled demo data (no EVE credentials, no network)
cargo run -- --demo
# (equivalently: MIMIR_DEMO=1 cargo run)

# Run live: sign in with EVE SSO from the Characters view
cargo run
```

### Running Tests

```bash
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

### Building for Release

```bash
cargo build --release   # binary at target/release/mimir
```
